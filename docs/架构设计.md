# 模板执行器与 loop_template 架构设计

本文描述当前有效的 scripted / `loop_template` 执行体系。

## 1. 总体架构

当前模板执行器的核心思想是：

```text
state_scripts/*.yaml
  |
  | 读取脚本配置
  v
game_bot.scripted.runner
  |
  | 识别为 template loop 脚本
  v
game_bot.scripted.loop_script
  |
  | 每轮截图、扫描模板、选择命中模板
  v
模板同名 JSON 元数据
  |
  | 定义优先级、点击区域、动作、结束标记、兜底标记
  v
game_bot.scripted.runtime
  |
  | 调用截图、识别、输入能力
  v
core / vision 底层能力
```

底层能力：

- 窗口发现与操作：`game_bot/core/window.py`
- 截图：`game_bot/core/capture.py`
- 输入：`game_bot/core/input.py`
- dm.dll 封装：`game_bot/core/dm.py`
- 模板匹配：`game_bot/vision/template.py`
- 模板分组与引用展开：`game_bot/vision/templates.py`

输入能力必须经过 `game_bot.core.input`，最终由注册的 `dm.dll` COM 后端执行。截图和模板识别仍沿用当前 Win32/GDI/mss/OpenCV 路径。

## 2. 核心模块职责

| 模块 | 职责 |
| --- | --- |
| `game_bot/scripted/runner.py` | scripted 脚本入口；列出脚本、解析脚本名、准备窗口、运行脚本 |
| `game_bot/scripted/loop_script.py` | `loop_template` 主实现；读取 `state_scripts/*.yaml`，循环扫描模板并执行动作 |
| `game_bot/scripted/runtime.py` | 脚本运行时；封装截图、匹配、点击、拖拽、按键、等待 |
| `game_bot/scripted/context.py` | 保存一次运行的上下文、截图路径、最近匹配、变量 |
| `game_bot/scripted/priority_match.py` | 按模板优先级分组扫描，并选择最佳命中 |
| `state_scripts/*.yaml` | 可复用状态流程；`start_flows` 引用同名流程完成入口/恢复逻辑 |
| `game_bot/scripted/components/popups.py` | 通用弹窗恢复占位模块；业务入口不再使用 component |

## 3. 脚本配置模型

`loop_template` 脚本位于：

```text
state_scripts/*.yaml
```

典型结构：

```yaml
script:
  id: example
  start_flows:
    - 返回主岛
  loop_dirs:
    - 弹窗
    - 地下城
  threshold: 0.85
  completion_count: 1
  scales:
    - 1.0
  save_debug: false
  no_match_recovery_rounds: 3
  no_match_recovery_wait_ms: 1000
```

解析后对应 `TemplateLoopScriptDefinition`。

| 字段 | 职责 |
| --- | --- |
| `id` | 脚本标识，默认取文件名 |
| `path` | 脚本 YAML 路径 |
| `start_flows` | 连续无命中后的入口/恢复状态流程列表，例如 `返回主岛` |
| `loop_dirs` | 要扫描的模板目录，基于 `templates/icons` |
| `end_template` | 额外指定的结束模板 |
| `threshold` | 模板命中阈值 |
| `completion_count` | success 模板累计命中多少次后完成 |
| `scales` | OpenCV 模板缩放匹配比例 |
| `save_debug` | 是否保存 debug 匹配图 |
| `no_match_recovery_rounds` | 连续无命中多少轮后执行恢复组件 |
| `no_match_recovery_wait_ms` | 无命中恢复前的等待间隔 |

目录引用规则：

- `loop_dirs` 只能指向 `templates/icons` 下的相对目录。
- 可以写 `弹窗`，也可以写 `templates/icons/弹窗`。
- 不能跳出 `templates/icons`。
- 每个目录只扫描当前层级的 `*.png`，不会递归扫描子目录。

## 4. 运行流程

主调用链：

```text
run_script_by_name()
  -> resolve_script()
  -> run_template_loop_script_by_name()
  -> load_template_loop_script()
  -> _run_template_loop_script()
  -> _run_loop_once()
  -> _execute_template_actions()
```

每轮 `_run_loop_once()` 的核心流程：

```text
1. 截取当前游戏窗口
2. 扫描 primary loop templates
3. 按 priority 分组匹配
4. 对命中模板检查 required/excluded 条件
5. 单独检查 success/end 标记模板
6. 根据结果分支：
   a. success 模板达到 completion_count -> 执行动作并结束
   b. end 模板命中 -> 执行动作并结束
   c. 普通模板命中 -> 执行动作，进入下一轮
   d. 无普通模板命中 -> 尝试 fallback 模板
   e. fallback 也无可执行 -> 记录 no_template_matched
7. 连续无命中达到阈值后先触发 Esc 恢复；Esc 恢复达到上限后执行 `start_flows` 状态流程恢复
```

外层 `_run_template_loop_script()` 负责：

- 初始化 `ScriptContext` 和 `ScriptRuntime`。
- 解析并缓存模板集合。
- 维护 `loop_index`。
- 维护连续无命中计数 `no_match_rounds`。
- 在连续无命中达到阈值时执行 Esc/状态流程恢复。
- 捕获 `ScriptPause`、`_TemplateLoopFinished` 和普通异常。

## 5. 模板集合分类

`_resolve_loop_templates()` 会从 `loop_dirs` 收集所有 PNG，然后按模板元数据分成几类。

| 类型 | 判定方式 | 执行时机 |
| --- | --- | --- |
| primary templates | 未标记 `is_non_standalone`，且未标记 `is_fallback_template` | 每轮主扫描 |
| fallback templates | 标记 `is_fallback_template` | 整轮无普通模板命中时 |
| end templates | 标记 `is_end_template`，或脚本配置 `end_template` | 每轮额外检查，命中后结束 |
| success templates | 标记 `is_success_template` | 每轮额外检查，累计达到 `completion_count` 后结束 |
| non-standalone templates | 标记 `is_non_standalone` | 不参与主扫描，只适合作为条件或链式模板 |

## 6. 优先级匹配策略

优先级逻辑在 `game_bot/scripted/priority_match.py`。

匹配语义：

```text
1. 读取每个模板的 priority，默认 0。
2. 按 priority 从高到低分组。
3. 先扫描最高优先级组。
4. 如果当前优先级组有命中，不再扫描更低优先级组。
5. 同组多命中时，按 priority、score、原始顺序选择最佳结果。
```

设计影响：

- 具体状态模板应设置更高优先级。
- 宽泛模板不要设置太高优先级，否则会遮蔽后续模板。
- 兜底动作模板应配置 `is_fallback_template`，不要参与主扫描。

## 7. 条件校验

模板命中后会执行 `_apply_template_preconditions()`。

支持两类条件：

- required：当前模板命中后，指定模板也必须命中。
- excluded：当前模板命中后，指定模板不能命中。

兼容字段名：

```text
postcondition_templates
postcondition_template
precondition_templates
precondition_template
requires_templates
requires_template

postcondition_not_templates
postcondition_not_template
excludes_templates
excludes_template
```

注意：这里的 `postcondition` 实际是在同一张截图上做“命中后附加条件校验”，不是动作执行后的等待。

## 8. 模板元数据设计

每个 PNG 模板可以有一个同名 JSON：

```text
templates/icons/<group>/button.png
templates/icons/<group>/button.json
```

常用字段：

| 字段 | 职责 |
| --- | --- |
| `priority` | 匹配优先级 |
| `actions` | 命中后动作列表 |
| `action` | 单个动作的兼容字段 |
| `ability` | 旧字段兼容 |
| `click_region` | 点击区域 |
| `click_regions` | 多个点击区域 |
| `coordinate_space` | 点击区域坐标系 |
| `is_end_template` | 结束标识模板 |
| `is_success_template` | 成功标识模板 |
| `is_non_standalone` | 非单独触发模板 |
| `is_fallback_template` | 兜底模板 |
| `group_match_limit` | 单模板累计命中上限 |
| `postcondition_templates` | 必须同时命中的模板 |
| `postcondition_not_templates` | 不能同时命中的模板 |
| `post_action_template` | 当前动作完成后继续匹配并执行的模板 |
| `post_action_template_threshold` | 后续模板匹配阈值 |
| `post_action_template_delay_ms` | 后续模板动作完成后的等待 |
| `end_template` | 当前模板动作完成后等待出现的结束模板 |

坐标系：

- `template`：相对模板左上角，执行时会按匹配缩放比例换算到窗口客户区。
- `window`：窗口客户区坐标。
- `screen`：屏幕坐标，会换算成窗口客户区坐标。
- `mixed`：用于 `click_regions` 中每个区域单独声明坐标系。

## 9. 动作执行模型

动作入口：

```text
_execute_template_actions()
```

如果模板没有配置动作，默认动作是：

```json
{"type": "click_match", "delay_after_ms": 500}
```

支持的动作类型：

| 动作 | 职责 |
| --- | --- |
| `none` | 不执行输入，只等待 |
| `click_match` | 点击当前匹配模板的点击区域 |
| `drag_match` | 从当前模板点击区域开始拖拽 |
| `drag_point` | 从固定点开始拖拽 |
| `wait` | 等待指定毫秒 |
| `key` | 按键 |
| `flow` | 调用同名状态流程 |
| `template` | 旧版模板链动作，当前迁移为 `post_action_template` |
| `log` | 输出日志 |
| `pause` | 暂停脚本 |
| `finish` | 结束脚本 |

动作底层由 `ScriptRuntime` 执行：

- `click_match()`
- `drag_match()`
- `drag_point()`
- `press_key()`
- `wait()`
- `match_first()`
- `expect_template()`

`ScriptRuntime` 负责把模板匹配结果转换成点击点、拖拽起点，并维护：

- `context.last_match`
- `context.last_match_click_point`
- `context.last_match_click_region`
- `context.step_index`
- `context.screenshot_path`

## 10. 后续模板链

`post_action_template` 用于表达：

```text
当前模板命中
  -> 执行当前模板 actions
  -> 重新截图
  -> 匹配 post_action_template
  -> 命中后递归执行该模板 actions
```

递归深度限制为 3，避免模板动作链无限递归。

如果后续模板没有命中，会抛出 `ScriptPause`，暂停原因类似：

```text
template_action_not_found:<template>
```

## 11. 结束与恢复机制

### 11.1 success 模板

`is_success_template` 表示“成功进度标识”。

命中后会累计：

- 总成功次数：`template_success_match_count`
- 单模板成功次数：`template_success_match_counts`

当总成功次数达到 `completion_count`，执行该 success 模板动作，然后结束脚本。

### 11.2 end 模板

`is_end_template` 或脚本的 `end_template` 表示“立即结束标识”。

命中后执行该模板动作，然后结束脚本。

### 11.3 fallback 模板

`is_fallback_template` 不参与主扫描。

只有当整轮 primary templates 都没有命中时，才按优先级尝试 fallback 模板。fallback 的匹配调用使用 `threshold=-1.0`，实际语义更接近“无命中时强制选择一个兜底动作模板”，而不是严格判断当前截图是否真的命中。

### 11.4 连续无命中恢复

如果一轮中没有普通模板命中，且 fallback 也没有处理，返回：

```text
no_template_matched
```

外层循环累计 `no_match_rounds`。达到 `no_match_recovery_rounds` 后，先通过 dm 输入触发 Esc 并重新循环；Esc 恢复达到上限后，会依次执行 `start_flows` 中的状态流程，例如 `返回主岛`。

## 12. 运行上下文

`ScriptContext` 保存一次脚本运行的状态：

| 字段 | 职责 |
| --- | --- |
| `hwnd` | 目标窗口句柄 |
| `script_id` | 脚本标识 |
| `run_id` | 本次运行唯一 ID |
| `step_index` | 步骤序号 |
| `screenshot_path` | 最近截图 |
| `last_match` | 最近模板匹配结果 |
| `last_match_click_point` | 最近点击点 |
| `last_match_click_region` | 最近点击区域 |
| `variables` | loop_template 计数、结果、恢复状态等 |
| `dry_run` | 只模拟不输入 |
| `background_mode` | 后台模式 |

输出目录：

```text
runtime/scripts/<run_id>/screenshots
runtime/scripts/<run_id>/debug
```

## 13. 工作台与 API

工作台相关代码主要在：

- `frontend/src/App.vue`
- `game_bot/web/window_bridge.py`

工作台负责：

- 管理模板分组。
- 裁剪并保存模板。
- 编辑模板元数据。
- 创建/编辑 template loop flow。
- 调用后端 API 执行脚本或预览匹配结果。

后端 bridge 中有模板元数据归一化逻辑，字段名需要和 `loop_script.py` 保持一致，例如：

- `actions`
- `postcondition_templates`
- `postcondition_not_templates`
- `post_action_template`
- `is_end_template`
- `is_success_template`
- `is_non_standalone`
- `is_fallback_template`

## 14. 当前注意点

1. `start_flows` 是连续无命中后的入口/恢复状态流程，不是严格意义的启动前流程。
2. `loop_script.py` 和 `runtime.py` 中部分中文日志已经乱码，需要后续统一修复编码。
3. fallback 模板当前是“整轮无命中时强制执行”的语义，配置时要谨慎。
4. `priority` 的遮蔽效应很强：高优先级组一旦命中，低优先级模板不会被扫描。
5. `postcondition_templates` 字段名容易误解，当前实际用于“同一截图上的附加命中条件”。
6. `post_action_template` 会重新截图并递归执行后续模板动作，适合表达短链路。
7. 模板元数据读取失败时通常回退为空配置，不会强制报错；这有利于兼容，但也可能掩盖 JSON 配置错误。

## 15. 推荐使用方式

新增一个玩法脚本时，建议：

1. 在 `templates/icons/<玩法名>/` 下放置该玩法主模板。
2. 把通用弹窗模板放到独立公共目录，例如 `templates/icons/弹窗/`。
3. 在 `state_scripts/<玩法名>.yaml` 中配置多个 `loop_dirs`。
4. 给具体状态模板配置较高 `priority`。
5. 给宽泛兜底模板配置 `is_fallback_template`，不要参与主扫描。
6. 对只能作为条件的模板配置 `is_non_standalone`。
7. 用 `is_success_template` 和 `completion_count` 表达完成次数。
8. 用 `is_end_template` 表达立即结束。
9. 用 `post_action_template` 表达短的动作后确认链。
10. 复杂业务动作优先沉淀为可复用状态流程，不要全部堆进模板 JSON。
