# 状态流程性能及日志优化设计

## 背景与目标

当前工作台里的“状态流程”实际对应 active template-loop YAML 流程，入口和职责可参考 `docs/模块索引.md:13`。流程页面负责编辑 `state_scripts/*.yaml`，后端通过 template-loop 执行器启动子进程，子进程循环截图、匹配模板并执行模板 sidecar actions。

本设计解决两个问题：

1. **状态流程执行性能卡点**：分析截图、模板匹配、元数据读取、优先级扫描、日志读取和前端渲染中的主要开销，并给出分阶段优化方案。
2. **日志与页面减负**：页面不再展示完整流程状态和实时运行日志，避免高频轮询、日志解析和 DOM 更新增加系统负载；完整日志改为实时输出到启动控制台，便于观察执行进度和卡点；页面只展示匹配失败信息，并保留匹配失败截图。

设计结论：

- **完整运行日志、进度日志、性能卡点日志统一输出到启动控制台。**
- **流程页面只保留匹配失败事件和失败截图。**
- **后端维护轻量 failure events，不再让页面通过完整日志文本反推状态。**
- **匹配主链路后续改为 in-memory screenshot + 预编译模板计划 + 单轮匹配缓存。**

## 当前执行链路

### 前端到后端

`frontend/src/App.vue` 的状态流程页包含流程列表、流程表单、YAML 预览，以及当前的“状态 / 运行日志”卡片：

- 页面工具栏和“日志自动刷新”：`frontend/src/App.vue:187`
- 流程列表和运行中/停止标签：`frontend/src/App.vue:196`
- 流程表单与模板预览：`frontend/src/App.vue:209`
- 当前状态/日志卡片：`frontend/src/App.vue:274`
- 未识别截图展示：`frontend/src/App.vue:290`

启动流程时，前端调用 `/api/template-loop-flows/{filename}/start`，后端在 `game_bot/web/window_bridge.py:993` 处理请求，最终调用 `loop_manager.start_flow(...)`。

当前日志读取路径：

- 前端调用 `/api/template-loop-flows/{filename}/logs`。
- `game_bot/web/window_bridge.py:946` 处理 `/logs`。
- `game_bot/scripted/loop_manager.py:202` 读取日志文件尾部。
- 后端把 `log` 和从日志中解析出的 `unrecognized_template` 返回给前端。
- 前端再用 `visibleFlowLog`、`flowProgressStatusSummary` 从日志文本中过滤日志和反推状态。

### 后端流程执行

后端启动链路：

1. `game_bot/web/window_bridge.py:993` 接收 start 请求，找到或准备窗口。

3. 子进程执行 `tools/run_template_loop_script.py`。

5. `run_template_loop_script_by_name()` 打开流程日志文件，并重定向 stdout/stderr。
6. `game_bot/scripted/loop_script.py:226` 的 `_run_template_loop_script()` 初始化 `ScriptContext` / `ScriptRuntime`，解析模板集合并进入循环。
7. 每轮调用 `game_bot/scripted/loop_script.py:368` 的 `_run_loop_once()`：截图、扫描主模板、检查 success/end、执行 fallback 或模板 actions。

单轮主流程中关键逻辑：

- 截图：`game_bot/scripted/loop_script.py:377`
- priority 扫描：`game_bot/scripted/loop_script.py:405`
- success/end 额外检查：`game_bot/scripted/loop_script.py:415`
- 无命中保存未识别截图：`game_bot/scripted/loop_script.py:491`
- 命中后执行模板动作：`game_bot/scripted/loop_script.py:516`

## 当前日志与状态链路的问题

### 页面状态是从文本日志反推的

当前页面上的“当前状态”不是后端结构化状态，而是前端从完整日志文本中解析出来的。这样会带来几个问题：

- 每次轮询都要下载日志文本。
- 前端 computed 要 split / regex 扫描日志。
- 日志内容越多，解析和渲染成本越高。
- 页面刷新频率和流程日志输出频率耦合，容易让 UI 成为运行负载的一部分。

### 后端读取日志文件方式偏重

`game_bot/scripted/loop_manager.py:202` 的 `read_log()` 当前读取日志文件内容后再截断尾部。即使前端只请求 `max_chars=12000`，后端也可能先读取较大的完整文件。长时间运行后，这个接口会越来越不适合作为页面实时状态来源。

### 子进程日志归属不清晰

`game_bot/scripted/loop_manager.py:121` 当前用 `CREATE_NO_WINDOW` 启动子进程，并把 stdout/stderr 写到日志文件。与此同时，`game_bot/scripted/loop_script.py:172` 又在子进程内部打开同一个流程日志文件并重定向 stdout/stderr。该模式让完整日志主要落在文件里，不利于“启动控制台实时观察”，也容易出现父子进程同时处理同一日志文件的复杂性。

## 性能卡点分析

### 1. 同一截图被每个模板重复读取和解码

`_run_loop_once()` 每轮只截图一次，但后续扫描每个模板时都会调用 `_match_on_capture(...)`。该函数最终调用 OpenCV 模板匹配逻辑，而当前匹配函数会按路径读取 source screenshot。

现象：

- 一轮截图得到一个 PNG 文件。
- 如果该轮扫描 80 个模板，就可能重复读取/解码同一张 PNG 80 次。
- 模板图本身已有缓存空间，但 source screenshot 没有按单轮复用。

优化方向：

- 一轮只解码一次截图。
- 匹配函数支持传入内存图像对象，而不是每个模板都从文件路径读取。
- 保留截图路径仅用于 debug、失败截图保存和日志定位。

### 2. 每轮截图都先落盘，成功后再删除

当前 `_run_loop_once()` 通过 `runtime.context.transient_screenshot_output_path(...)` 生成临时截图路径，然后 `runtime.capture_client(...)` 写入文件。成功命中后，代码会删除该临时截图。

这意味着常规成功路径也会产生大量磁盘写入和删除：

- 截图写 PNG。
- 匹配阶段又多次读取 PNG。
- 成功后删除 PNG。

优化方向：

- 主路径使用内存截图。
- 只有以下情况落盘：
  - 匹配失败，需要保留未识别截图。
  - `save_debug=True`。
  - 异常/暂停需要保留诊断截图。

### 3. 模板 sidecar JSON 元数据重复读取

template-loop 中很多判断都依赖模板同名 JSON：优先级、阈值、actions、success/end/fallback、precondition、group_match_limit 等。当前这些字段运行中按需读取，复杂流程里同一模板的 JSON 可能在一轮内被读多次。

优化方向：

- 流程启动时一次性读取并解析 metadata。
- 构建只读的 `TemplateLoopPlan`。
- 每轮只访问内存中的计划对象，不再反复打开 JSON 文件。

### 4. 优先级分组和排序可预编译

`priority_match.py` 的职责是按模板 priority 分组扫描，并在同优先级内按 score 选择最佳命中。模板集合和 priority 在一次流程运行中基本稳定，没有必要每轮重复构造分组。

优化方向：

- 启动流程时预构建 priority groups。
- 每轮只处理动态条件，例如 group match limit。
- 输出计划摘要：模板总数、主扫描模板数、success/end/fallback 数量、优先级分布。

### 5. flagged / precondition / fallback 可能重复匹配

同一轮里可能出现以下重复：

- 主扫描检查过的模板，又被 success/end flagged 检查复用或重查。
- 多个候选命中后，precondition/exclusion 可能检查相同依赖模板。
- fallback 扫描可能对同一截图继续做额外匹配。

优化方向：

- 单轮维护 match cache。
- key 至少包含：`screenshot_id`、`template_path`、`threshold`、`scales`、`region`。
- action 后如果重新截图，则新截图使用新的 cache，避免复用过期结果。

### 6. scaled templates 未做充分缓存

多尺度匹配会对模板图片进行 resize。如果某个流程启用了多个 scale，重复缩放成本会明显增加。

优化方向：

- 缓存缩放后的模板图。
- cache key 包含模板路径、mtime、scale。
- 模板文件修改后自动失效。

### 7. 前端完整日志轮询和渲染造成额外负载

当前页面每 2 秒拉取日志；调度器执行时还存在更频繁的进度轮询。前端拿到日志后还要过滤、解析和渲染。对于“观察进度和卡点”这个需求，页面不是合适载体；控制台输出更实时、开销更低。

优化方向：

- 页面不再拉取完整日志。
- 控制台承载完整日志和性能日志。
- 页面只拉取结构化 failure events，数据量很小。

## 日志与页面展示优化设计

### 总体决策

| 日志/信息类型 | 输出位置 | 是否进入页面 |
| --- | --- | --- |
| 启动、停止、流程进度 | 启动控制台 | 否 |
| 每轮耗时、慢模板、匹配统计 | 启动控制台 | 否 |
| template action 执行日志 | 启动控制台 | 否 |
| 异常栈、暂停原因 | 启动控制台；必要时 failure event 摘要 | 页面只显示摘要 |
| 没有模板达到阈值 | 启动控制台 + failure event | 是 |
| 没有可用模板匹配结果 | 启动控制台 + failure event | 是 |
| 未识别截图 | failure event + 现有图片预览 | 是 |

### 控制台实时输出

推荐由 `TemplateLoopProcessManager` 统一管理子进程输出：

1. 启动子进程时使用 `stdout=subprocess.PIPE`、`stderr=subprocess.STDOUT`、`bufsize=1`、文本模式。
2. 为每个 managed process 启动一个 reader thread。
3. reader thread 逐行读取子进程输出：
   - 立即写入父进程 stdout，并加上流程名前缀。
   - 可选继续追加到诊断日志文件。
   - 解析匹配失败相关行，写入 `recent_failure_events`。
4. 页面不再消费完整 stdout 日志。

推荐前缀格式：

```text
[template-loop:世界BOSS.yaml] [2026-07-07T12:00:00] [template-loop] 第 8 轮：没有模板达到阈值；最高得分模板=...；得分=0.731
```

性能日志格式建议：

```text
[template-loop][perf] round=42 capture_ms=31.2 match_ms=184.6 templates_checked=37 precondition_ms=12.5 action_ms=501.0 total_ms=732.4 selected=...
[template-loop][slow-match] round=42 template=xxx.png cost_ms=86.4 threshold=0.82 score=0.76
[template-loop][failure] round=43 reason=no_template_matched screenshot=templates/icons/.../未识别/xxx.png
```

### 页面 failure-only 展示

流程页面保留的内容：

- 流程列表、运行中/停止标签。
- 流程表单、模板目录、YAML 预览。
- “匹配失败 / 未识别截图”卡片。

流程页面移除的内容：

- “当前状态”摘要。
- 完整运行日志 `<pre>`。
- 进度类日志过滤展示。
- `日志自动刷新` 作为完整日志开关。

failure-only 卡片建议展示：

- 最近一次匹配失败时间。
- 失败原因。
- 最高得分模板和分数（如果有）。
- 未识别截图预览。
- 截图路径。
- `制作为模板` 按钮。
- 可选：最近 N 条失败事件列表，默认 N=20。

无失败时显示：

```text
暂无匹配失败。
完整运行进度和性能日志请查看启动控制台。
```

## 后端 API 设计

### 保留现有流程控制 API

继续保留：

- `GET /api/template-loop-flows`
- `GET /api/template-loop-flows/{filename}`
- `POST /api/template-loop-flows/{filename}/start`
- `POST /api/template-loop-flows/{filename}/stop`
- `DELETE /api/template-loop-flows/{filename}`

这些接口仍负责流程列表、运行状态、启动停止和配置保存。

### 新增 failure events API

推荐新增：

```http
GET /api/template-loop-flows/{filename}/failures?limit=20
```

返回示例：

```json
{
  "ok": true,
  "filename": "世界BOSS.yaml",
  "running": true,

    {
      "timestamp": "2026-07-07T12:00:00",

  }

```

### `/logs` 的兼容处理

`/logs` 可以保留作临时兼容和诊断入口，但不再作为页面默认轮询接口。

建议策略：

- 第一阶段：保留 `/logs`，但前端不再自动调用。
- 第二阶段：将 `/logs` 标记为 debug-only。
- 第三阶段：若仍需页面诊断日志，增加手动“下载诊断日志”能力，而不是实时渲染。

### manager 内部状态

`ManagedTemplateLoopProcess` 建议增加或维护以下轻量字段：

- `last_message`：最近一条控制台日志摘要。
- `recent_failure_events`：最近 N 条失败事件。
- `latest_unrecognized_template`：最新未识别截图。
- `output_thread`：stdout reader thread。
- `log_path`：可选诊断日志路径。

注意：failure events 要按流程文件名或进程隔离，避免多流程并发时串线。

## 前端改造设计

### 流程页

当前 `frontend/src/App.vue:274` 的“状态 / 运行日志”卡片改为“匹配失败 / 未识别截图”卡片。

移除或停用：

- `flowLog` 的完整日志用途。
- `visibleFlowLog`。
- `flowProgressStatusSummary`。
- `isFlowProgressStatusLine`。
- `flowLogAutoRefresh`。
- `flowLogTimer`。
- `updateFlowLogTimer` 对完整日志的轮询。
- `loadFlowLog()` 对 `/logs?max_chars=12000` 的自动读取。

新增或保留：

- `flowFailureEntries`。
- `flowFailureTimer`，如仍需要低频刷新 failure-only 数据。
- `flowUnrecognizedTemplate`，继续用于展示失败截图。
- `loadFlowFailures()`，调用 `/failures`。

刷新策略：

- 流程运行时低频刷新 failure events，例如 3-5 秒一次。
- 或先只提供手动刷新按钮，降低第一版改动风险。
- 不再因 `flowUnrecognizedTemplate` 存在而每次都 `refreshTemplates()`；只在截图路径变化时刷新，或者直接使用 failure event 中的截图路径展示。

### 调度器页

调度器页中重复的状态/日志卡片也应同步移除或改为 failure-only 展示，否则仍会保留一条完整日志轮询和渲染路径。

调度器页面保留：

- 队列状态。
- 当前执行项。
- 成功/失败结果。
- 当前或最近失败流程的 failure-only 信息和截图。

不保留：

- 完整运行日志框。
- 从日志文本反推流程状态的 UI。

## 执行性能优化设计

### P0：页面减负与日志链路调整

优先做，因为收益大、风险相对低。

改造内容：

1. 后端子进程日志实时输出到启动控制台。
2. 页面下线完整状态/日志展示。
3. 前端停止自动轮询 `/logs`。
4. 后端新增 failure events 或复用轻量 failure-only 数据。
5. 页面保留匹配失败信息和未识别截图。

预期收益：

- 页面不再因日志增长变卡。
- 后端不再因页面刷新反复读完整日志。
- 用户能在控制台实时看到完整进度和卡点。

### P1：截图和模板匹配缓存

改造内容：

1. 增加内存截图接口，例如 `runtime.capture_client_image(...)`。
2. 增加可接受 source image 的模板匹配函数，例如 `match_template_image(...)`。
3. 一轮截图只解码一次，所有模板复用同一 image。
4. 失败或 debug 时再把 image 写到文件。
5. 缓存 scaled templates。

预期收益：

- 明显减少同图重复读盘和 PNG 解码。
- 多模板、多 scale 场景收益最大。

### P1：TemplateLoopPlan 预编译

建议引入运行计划对象：

```python
@dataclass(frozen=True)
class PlannedTemplate:
    path: Path
    relative_path: str
    metadata: dict[str, Any]
    priority: float
    threshold: float
    actions: tuple[dict[str, Any], ...]
    is_end: bool
    is_success: bool
    is_non_standalone: bool
    is_fallback: bool
    group_match_limit: int | None
    required_templates: tuple[Path, ...]
    excluded_templates: tuple[Path, ...]

@dataclass(frozen=True)
class TemplateLoopPlan:
    all_templates: tuple[PlannedTemplate, ...]
    primary_groups: tuple[tuple[float, tuple[PlannedTemplate, ...]], ...]
    fallback_templates: tuple[PlannedTemplate, ...]
    end_templates: tuple[PlannedTemplate, ...]
    success_templates: tuple[PlannedTemplate, ...]
```

构建时机：流程启动后、进入循环前，也就是当前 `game_bot/scripted/loop_script.py:250` 附近解析模板集合的位置。

预期收益：

- metadata JSON 只在启动阶段读取。
- priority 分组只构建一次。
- 每轮循环逻辑更清晰，可直接输出计划摘要。

### P2：单轮匹配结果复用

改造内容：

- 每轮创建 `TemplateRoundMatcher`。
- 所有主扫描、flagged、precondition、fallback 都通过它匹配。
- 内部按 `(template_path, threshold, scales, region)` 缓存结果。

注意：

- 只在同一截图内复用。
- action 后如果改变画面，必须进入下一轮或重新截图，不能复用旧结果。

### P2：性能埋点

建议在以下位置加 `perf_counter()`：

- `_run_loop_once()` 总耗时。
- `runtime.capture_client()` 截图耗时。
- 主模板扫描耗时。
- flagged / precondition 耗时。
- action 执行耗时。
- 未识别截图保存耗时。

控制台输出规则：

- 默认每轮输出一行 summary。
- 单模板耗时超过阈值时输出 slow-match。
- 支持配置或环境变量控制详细程度。

## 分阶段实施建议

### 阶段一：日志链路和页面减负

目标：先满足用户当前最直接的诉求。

1. `loop_manager.py` 改为读取子进程 stdout 并实时转发到启动控制台。
2. 新增或整理 failure events 数据结构。
3. `window_bridge.py` 提供 failure-only API。
4. `App.vue` 删除完整状态/日志 UI，改为匹配失败卡片。
5. 调度器页同步去掉完整日志展示。

### 阶段二：低风险缓存与观测

目标：用较小改动降低固定开销，并能看见真实耗时。

1. 增加每轮耗时 summary。

## 验证标准

### 日志与页面

- 启动流程后，启动控制台能实时看到完整流程日志。
- 控制台能看到每轮耗时、慢模板、未识别截图路径等关键观察信息。
- 流程页面不再显示完整运行状态、进度摘要和完整日志框。
- 流程页面只显示匹配失败信息。
- 匹配失败时，页面仍能展示失败截图，并能继续进入“制作为模板”的路径。
- 调度器页不再重复展示完整运行日志。

### 后端负载

- 页面不再定时请求 `/logs?max_chars=12000`。
- 后端不再为了页面状态刷新反复读取完整日志文件。
- 长时间运行后，日志文件变大不会导致页面刷新变慢。
- 多流程并发时 failure events 不串线。

### 模板执行行为

- 优化前后模板匹配结果一致。
- success/end/fallback 语义不变。
- precondition/exclusion 语义不变。
- dry run 和 background mode 行为不变。
- 异常退出时控制台能看到错误摘要；必要时 failure event 能显示错误摘要。

### 性能收益观察

- 单轮总耗时、截图耗时、匹配耗时能在控制台观察。
- 同一模板/同一截图重复匹配减少。
- 磁盘临时截图写入次数减少。
- 前端 CPU 和内存不随日志增长持续增加。

## 风险与注意事项

1. **无控制台启动场景**  
   如果后端以无控制台方式启动，实时控制台日志不可见。建议保留诊断日志文件或提供手动导出诊断日志能力。

2. **Windows PIPE 阻塞**  
   如果使用 `stdout=PIPE`，必须持续读取子进程输出，避免管道缓冲区满导致子进程阻塞。

3. **多流程并发**  
   failure events 必须按 flow filename / pid 隔离。控制台日志也应加流程名前缀。

4. **截图路径安全**  
   返回给前端的截图路径必须继续使用现有安全路径和模板预览逻辑，避免任意路径读取。

5. **页面状态减少后的可观察性**  
   页面不再显示完整状态后，用户判断流程是否运行应依赖流程列表中的 `运行中/停止` 标签、按钮状态和控制台日志。

6. **兼容旧 `/logs` 调用**  
   第一阶段可以保留 `/logs`，但前端默认不调用。后续如清理，应确认没有其他页面或工具依赖完整日志返回。

7. **现有 action 调用签名需复核**  
   `game_bot/scripted/loop_script.py:449`、`game_bot/scripted/loop_script.py:467`、`game_bot/scripted/loop_script.py:516` 等位置调用 `_execute_template_actions(..., current_definition=definition)`；同时函数定义和 `flow` action 内部变量使用看起来需要复核。该问题不属于本设计文档的直接实现范围，但建议在后续修改日志/执行链路前先处理，避免优化时掩盖已有 correctness 风险。
