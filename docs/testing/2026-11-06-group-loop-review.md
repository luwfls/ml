# 分组循环专项测试与页面交互分析

来源：SCM-880 评论 `bb90e94f-2e74-441f-a185-d5375f10ec8e`。测试基线：`ed0b9954592f7bd21e26ee4de31905939faca394`。环境：Linux、Chromium 150、Python 3.14，The Internet 固定源码的本地页面、临时工作台数据，无账号、外部业务数据或真实安卓设备。

## 结论

**有明显优化空间，且当前没有可独立验收的“分组循环模式”页面入口。** 分组目前负责管理/筛选 State；F6 是一次截图预览；流程页“按分组添加”是将当时的成员 ID 加入流程草稿，不是保存一个动态分组引用。

本次不只执行已保存流程：完成 5 项分组页面检查、4 项按组成员构成候选集合的原生引擎检查，并复现 5 项交互/建模问题。9 项现有行为检查通过，不代表缺失的分组循环页面已验收。**旧预览结果串组问题已复现，尚未修复。** 本轮按“测试和分析”范围交付，不新增产品运行模式或修改页面。

| 优先级/编号 | 实测现象 | 对使用者的影响 | 建议 |

| P0 / UX-05 | 延迟复选框组预览请求，切换到3成员元素组后，旧组4项结果仍返回并显示；截图 `group-late-preview.png` | 把旧组结果当成当前组结果，可能据此错误调整State | 分组/截图/搜索上下文变化时清空结果；请求带上下文版本，丢弃过期响应；结果区明确显示来源组、截图和成员数 |
| P1 / UX-01 | State分组页没有独立循环/步进入口，只有F6预览；截图 `groups-no-loop-entry.png` | 为临时测试一个分组，必须转到流程页理解和配置流程 | 在选中分组旁提供“预览一次 / 步进测试 / 自动循环”；运行使用本次组成员快照，不强制生成已保存流程 |

## 建议的交互结构与验收条件

保留 State 制作页，在分组区域增加一块紧凑的“分组测试”面板：选定分组、成员总数与角色统计、目标设备、仅识别/实际输入、目标成功次数、轮数/超时，随后是预览、步进、自动循环按钮。启动确认显示实际设备和本次固定成员范围；空组或无成功State直接解释原因。运行区显示当前组、本次快照成员数、当前命中名称、成功次数和停止原因，可就地下一步、暂停、继续、停止并打开历史。

数据语义建议沿用当前安全边界：启动时固定成员和配置，组内后续编辑只影响下一次运行。已有`/api/debug/start`接受临时草稿，可作为复用方向；“分组来源/成员快照”需单独记录并展示，不能仅换一个流程名称冒充完整分组模式。

建议先处理UX-05和UX-02，避免显示或测试范围误导；再实现分组测试入口和启动前说明。后续验收至少包含：

1. 无需保存流程，从选定组直接启动自动或步进；请求中的成员与确认面板一致。
2. 切组、换图、修改筛选后，迟到预览不会串组；整组/筛选范围明确。
3. 实际执行两次成功周期，截图/动作及独立页面状态均可核验；仅识别不执行输入。
4. 运行期间换组不改变当前成员快照；暂停/继续/取消确认后行为稳定。
5. 空组、无成功State、多个终态、初始已成功均有可理解反馈；保留合法多成功场景，不用一刀切禁用代替解释。
6. 分组运行历史可以重开，记录来源、成员与版本；不能仅用成功toast作为验收。

## 复现

先按项目说明构建前端，并在兼容Python环境中安装`requirements-platform.txt`和`examples/the-internet/requirements.txt`。已有Chromium可直接使用：

```bash
.venv/bin/python tests/group_browser_probe.py --chromium /path/to/chromium --artifacts /path/to/new-group-evidence
```

脚本输出9项现有行为检查，以及单列的`observations.json`。观察中包含已知问题，不应把脚本退出0解读为分组模式全部验收通过。测试过程中只延迟原始预览请求来复现串组，没有伪造业务响应。每次使用新的证据目录；服务、浏览器、组成员数据均临时隔离并在前台收尾。

脚本编制阶段修正了事件等待、输入焦点下快捷键和按钮名称定位问题，未改变业务预期或产品实现；这些未完成的准备执行不作为产品“三轮失败”计数。最终完整执行9项检查全部完成，报告保留产品问题与能力缺口，不声称已修复。
